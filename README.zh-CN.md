# magpie-nearest-expiry

这是一个 magpie 目录型插件，注册 `nearest-expiry/nearest-expiry` 路由策略，并从本机网关定时刷新配额账本。

策略会优先选择额度最早失效的候选席位，综合使用：

- magpie 暴露给 JavaScript 策略的 seat 字段，例如 `soon`、`used`、`resting`；
- hooks 从 magpie 本机配额接口提取、按账号区分并写入 `AUTO_BOOK` 的窗口时间戳；
- 少量供应商语义修正，用于区分计数器窗口、每日额度和会作废的积分批次。

额度窗口按账号分别记录，同一供应商的两个账号不会混用过期数据。针对 CodeArts，限时批次直接由窗口自带的 `runsOutAt`/`runsOut` 识别，不再读中文 display 文案：厂商修复后只有真批次才会带这两个字段。批次剩余不足 10 积分时按已烧完处理，写入耗尽占位，避免小额尾量把账号继续挂在第一档、在 `stays=turn` 下被反复粘住请求并转而消耗长时效赠送积分。同步侧与策略侧使用同一个 10 积分阈值，避免两层判断不一致。

有些供应商用 `resetsAt` 描述每日签到或每日领取额度，但这类额度到时作废而非重置。窗口名标明是每日签到或今日积分且仍有余额时，账本会写入 `d` 标记，让它豁免短窗口过滤，一直参与到真正过期为止；已烧完的签到窗不进账本。烧完（剩余为 0）的重置窗同样按耗尽处理，写入耗尽占位，避免额度已尽的账号继续挂在临期档上。

账本只在排序语义变化时重写：策略排序只依赖 r 时刻与 o/d/w/s/x 标记的存在性，o 的数值抖动（随消耗变小）不改变这些离散特征时跳过写入，避免每次同步都热重载并清空策略里的同档轮换游标。

会到点作废的月度额度按作废量处理：CodeArts 从 0.3.25 起把 runsOutAt/runsOut 挪到「总积分」、分项桶不再带，而「总积分/基础积分包」的月度余额当月用不完即作废，所以同步侧用它的 resetsAt 作到期键、remaining 作废量（o）进第一档优先烧；烧完当前批次后自动回落到这个月度窗，而不是写 x 停在第一档之外。opencode-go 的 Month 窗同理带 o；它的 7 days 窗带 w 标记，只在到期时刻与其他供应商完全相同时排后，时间更早时仍按精确时间排前。opendesign 的 7 days 窗到点用不完会连累整月，按普通到期窗参与排序。opencode-go 与 opendesign 的 5 小时速率窗到点只是刷新、剩余不结转也不亏，不参与第一档排序。

订阅制窗（opencode-go/opendesign/commandcode 这类，remaining 是百分比、无计量单位）的额度不用就是亏，尾量同样进排序：这类窗豁免 MIN_RUNSOUT 绝对量阈值，账本打 s 标记，哪怕只剩 5% 也作为作废量 o 参与排序。积分类窗（积分/credits/points）继续按绝对量阈值过滤无价值尾量，每日签到窗按作废处理不算订阅制。

插件 options 可按时段给供应商降权：`timeRules` 按前缀匹配 seat key，`days`（UTC+8 星期，0=周日）与 `windows`（`[["08:30","22:00"]]` 分钟级、左闭右开）命中时，该供应商排到同组末尾作为软降权，其他候选都不可用时仍可兜底。前缀按边界匹配，`workbuddy` 不会误伤 `workbuddy-ai`。若账号的有效排序键按 UTC+8 自然日算在 `deferDueDays`（默认 4）天内到期，则豁免降权保持正常使用，临期额度照常烧完。降权候选不参与同档轮换。注册表 `magpie.options` 给出默认值，可用 `magpie plugin options` 覆盖。

有峰谷价的供应商由 `peakPricing` 列出，默认是 magpie 官方按小时计费的 4 类（deepseek、commandcode、opencode-go、ollama-cloud）加单独维护的 workbuddy。策略按时段切换偏好：谷价时段有峰谷价账号优先（此时按峰谷计费最便宜），峰价时段无峰谷价账号优先，把按峰谷计费的额度留到低谷。小窗口指每日签到窗和 24 小时内到期的积分批次，这类额度计价固定，谷价时段被压后，留到峰价时段使用。账号距到期不足 16 小时时进入临期保护，无视峰谷按到期优先烧，因此等不到下一个峰价时段的小窗口也能及时用掉。峰价时段采用 opencode-go 的工作日 09:00-12:00、14:00-18:00 口径，workbuddy 例外，按它自己的每天 08:30-22:00 判定。峰谷偏好是软排序层，临期额度始终压过它，也不会改变已用尽与无到期数据的分组。

opencode-go 的月窗剩余不足 20% 时，周窗不再作为排序键。周窗到点刷新，本身不用不亏，但把它当排序键会把账号顶到第一档、提前烧掉月窗余额；剔除后该账号退到后段，让位给真正临期作废的账号。月窗重置后剩余回到 100%，规则自动失效。

opencode-go 随时可用，积分类账号（带失效批次的）可能因限额用不完。排序时按 UTC+8 同一天判断：若两个候选的有效排序键（最早窗）落在同一天，带 o 的积分类账号排前；跨天仍按精确到期时间排序，不做任何调整。判断在策略侧实时进行，窗口烧完导致最早窗切换时当场生效，不依赖账本写盘那一刻的快照。

账号没有任何会作废或会到期的窗口时，账本写入 `x` 耗尽占位。占位会让该账号继续命中账本，从而屏蔽 seat 里可能滞后的 `soon` 与 `lapse`，但不提供排序用的到期时间，账号按无到期数据处理、回落到后段。这样限时额度烧完后，新回合会尽快切回仍有临期额度的账号。同步间隔为 5 分钟，决定这一回落被感知到的滞后上限；`stays=turn` 下同一长回合内的旧粘性仍由 magpie 核心保持，策略只影响新回合。

候选按最早到期的精确时间戳排序。只有到期时刻完全相同时，才用已用比例决胜；不把到期时间按小时取整，因为分钟级的先后会被不同额度池的用量比例反转。与最早到期相差 5 分钟内的候选视作同一档，按组轮换，避免分钟级差异把每轮对话都钉在同一个账号上。轮换状态保存在策略模块内、按 pool 区分；额度数据变化导致中间件重载时会清零。轮换只在有效排序键除到期时间与用量外都等价的候选间进行：同日积分类优先、同刻 7d 弱窗让位、峰谷时段偏好都比分钟级差异更重要，不会被轮换顶掉，各自的轮换游标也彼此隔离。

超过 30 天才到期的窗口按无到期数据处理，长时效额度不会和临期窗口争第一档。整桶已用比例达到 98% 的账号通常按已用尽垫底；如果账本里仍有 30 天内会作废的批次或 48h 内到期的窗口（含每日签到），它豁免这条规则并回到第一档，先把临期额度烧完再回落。

hooks 只在账本内容变化时写文件，不再写入周期性时间戳，避免每次同步都重载一次并清空轮换状态。相对当前时间计算的短速率窗会被排除，时间戳与失效量也会取整，使常规额度读数生成相同的账本。响应里没有有效账号时不会写账本，避免一次刷新失败把已有账本清空。

hooks 入口在 magpie 插件宿主内运行一个 5 分钟定时器。它不向模型暴露工具，也不改请求体，只刷新 middleware 入口文件里的账本块，由 magpie 热重载策略。

## 耗尽账号在同一长回合内跳过（onAccount）

`stays=turn` 的粘性会在每个请求里把上次答复的账号强制提到首位，策略排到末尾也拦不住同一长回合内的继续消耗。插件导出 `onAccount(account, ctx)`：hooks 每 5 分钟把限时额度已烧完（账本 `x` 占位）账号的匿名 ref 写入 `AUTO_SKIP` 块，`onAccount` 命中即返回 `{skip:true}`，magpie 直接试下一个候选；答复成功后粘性改写到新账号，同一长回合从下一次请求起就不再回到耗尽账号。

跳过的账号来自 magpie 配置的 `nearest-expiry/nearest-expiry` 组，其他策略的组不受影响。只有当耗尽账号所在的全部组都没有其他可用账号时，才不跳过它（整组兜底），避免所有候选被跳过导致请求失败。ref 是 magpie 对账号的匿名标识，hooks 用与 magpie 源码一致的 HMAC-SHA256 从 `account-ref.key`、`user`、`plan` 算出；key 尚未生成时名单为空，等首次 onAccount 触发 magpie 创建 key 后的下一轮同步再生效。首次核对可临时把 options 的 `debugRefs` 设为 true，日志会打印各账号的 `(provider, ref)`。

多窗口账号的小窗口（签到或 24 小时内的积分批次）烧完后，若不做处理，turn 粘性会留在它上面继续消耗剩下的长效窗。hooks 每轮同步时对比各账号的最早窗，发现短窗变成短窗以外的窗口就记一条交接事件，同时记下当前全组最早到期账号的 ref。onAccount 只在别人是最早、且该账号剩余最早窗超过 16 小时的情况下，把这个账号跳过最多 10 分钟，让长回合切到更紧急的席位；若它自己就是最早、或剩余窗已进入临期带，则放行，继续在同一账号上烧而不丢缓存。判断只读预计算好的最优 ref 加一次账本查询，不增加每请求的排序开销。

## 安装

```bash
magpie plugin add github:owner/magpie-nearest-expiry
magpie group set <group-id> routing=nearest-expiry/nearest-expiry stays=turn
```

包名使用 `middleware-nearest-expiry`，这样 magpie 的 `ShortName` 仍为 `nearest-expiry`，现有路由 id 不会变化。

## 运行时数据

发布源码只包含空的 `AUTO_BOOK` 占位块。运行时，hooks 使用临时文件加 rename 的方式，把供应商窗口时间戳写入该块。日志保存在：

```text
~/.config/magpie/nearest-expiry/sync-expiry.log
```

仓库不提交账号标识、额度快照或运行日志。

## 文件

- `nearest-expiry.middleware.js`：兼容 moejs 沙箱的路由策略。
- `sync-expiry.hooks.js`：运行在 Bun 宿主中的配额同步与源码注入。
- `package.json`：声明 middleware 与 hooks 两个 magpie 入口。

## 说明

- `package.json` 里的 `magpie.options` 只作为 magpie 选项编辑器的初始示例。运行时配置来自 `plugins.json` 中该插件的 `options` 条目。
- 对 GitHub 来源执行 `magpie plugin update` 可能替换安装目录。hooks 定时器会在重载后很快重新填充 `AUTO_BOOK`。
- 建议保持 `stays=turn` 或 `stays=off`。使用 `stays=auto` 时，magpie 的缓存亲和性可能让自定义路由策略无法在每个新回合重新参与决策。
